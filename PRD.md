## 1. Назначение документа

Этот PRD является главным рабочим продуктовым документом проекта.  
Он нужен не для разового описания идеи, а для ведения проекта до его завершения.

Документ фиксирует:

- что именно мы строим;
- какую проблему решает продукт;
- что входит в MVP;
- как должен работать агент;
- какие входы он принимает;
- какой результат он обязан выдавать;
- когда система должна спрашивать пользователя;
- какие ограничения и риски считаются критичными;
- в каком порядке проект должен развиваться дальше.

Этот файл становится основным живым PRD проекта.  
Исходные файлы `RAAEN.md.txt`, `PRD.md.txt` и `TZ.md.txt` остаются source context, но дальнейшая продуктовая работа ведется через этот документ.

Связанные рабочие документы:

- `ROADMAP.md` - фазы исполнения и критерии выхода;
- `BACKLOG.md` - приоритеты, эпики, фичи и ближайшая рабочая очередь.
- `TEXT-POLICY-MATRIX.md` - правила текста по разделам документа;
- `WORDING-RULES-BY-SECTION.md` - конкретные правила формулировок по разделам `מסמך משמעויות`;
- `MASMACH-SECTION-CONTRACTS.md` - контракты секций итогового документа;
- `QUANTITY-RULE-MATRIX.md` - правила quantity logic по типам работ.
- `ANCILLARY-WORKS-POLICY.md` - политика по сопутствующим работам и ограничениям auto-inclusion.

## 2. Продуктовое видение

`MASHMAUET Agent` - это управляемая AI-система для подготовки документа `מסמך משמעויות` на основе объяснения работ, дополнительных материалов и структурированных источников расчета.

Система не должна быть "свободным чатом", который просто пишет красивый текст.  
Она должна быть контролируемым рабочим механизмом, который:

- понимает, какие работы реально имеются в виду;
- подбирает релевантные позиции из `DEKEL`;
- при необходимости учитывает `MAVNADIM` как отдельный источник готовых модульных объектов;
- считает стоимость и агрегирует суммы;
- собирает итоговый документ в формате, близком к реальному `מסמך משמעויות`;
- явно показывает спорные места, assumptions и все зоны, где нужен review.

Главная ценность продукта:

- сократить время подготовки документа;
- снизить количество ошибок в подборе позиций и сумм;
- сделать процесс прозрачным и повторяемым;
- уменьшить зависимость от личного опыта конкретного сотрудника;
- довести подготовку `מסמך משמעויות` до полуавтоматического, но управляемого режима.

## 3. Проблема

Сейчас подготовка `מסמך משמעויות` сложна по нескольким причинам:

- описание работ часто дается в бытовой, неполной или смешанной форме;
- один и тот же кейс может прийти как текст, фото, документ, PDF, рукописная заметка или смесь источников;
- `DEKEL` большой и сложный для ручного поиска;
- неочевидно, какие позиции действительно соответствуют смыслу работы;
- часть сопутствующих работ может быть не названа явно;
- итоговый документ должен соответствовать формату шаблона, а не просто содержать список найденных строк;
- ошибки в matching, unit, quantity и aggregation приводят к неверному документу, даже если текст выглядит правдоподобно.

## 4. Цели продукта

### 4.1. Основные цели

1. Построить управляемый pipeline подготовки `מסמך משמעויות`.
2. Научить систему понимать объяснение работ из разных форматов входа.
3. Научить систему подбирать кандидатов из `DEKEL` точнее, чем простой keyword search.
4. Собрать корректный блок `אומדן` на основе подтвержденных строк и расчетов.
5. Сформировать итоговый документ в повторяемом шаблонном формате.
6. Сделать обязательный review-gate там, где данные неоднозначны.
7. Обеспечить traceability: от итогового документа до выбранных строк, допущений и уточнений.

### 4.2. Не-цели MVP

- полный автономный режим без review;
- универсальная поддержка любых типов шаблонов с первого релиза;
- идеальное OCR/handwriting extraction как обязательная часть MVP;
- автоматическое принятие спорных hidden works без подтверждения;
- замена доменного специалиста там, где реально требуется экспертное решение.

## 5. Пользователи и роли

### 5.1. Operator

Основной пользователь, который запускает кейс и доводит его до результата.

Задачи:

- создать кейс;
- передать объяснение работы и supporting evidence;
- просмотреть анализ;
- ответить на уточняющие вопросы;
- выбрать или подтвердить строки `DEKEL`;
- просмотреть preview и итоговый output;
- передать кейс на подтверждение или завершить его.

### 5.2. Reviewer

Пользователь с большей доменной уверенностью.

Задачи:

- проверить спорные кандидаты;
- подтвердить или отклонить позиции;
- проверить aggregation;
- проверить assumptions и warnings;
- подтвердить итоговый документ.

### 5.3. Admin / Knowledge Maintainer

Роль поддержки справочников и шаблонов.

Задачи:

- обновлять `DEKEL`;
- обновлять `MAVNADIM`;
- поддерживать mapping rules;
- поддерживать шаблон документа;
- вести библиотеки hidden works и служебные словари;
- контролировать качество данных и версий.

## 6. Источники входа

Система должна поддерживать не один жесткий формат входа, а несколько возможных форм:

- typed text;
- plain text document;
- PDF / presentation / infographic;
- handwriting image;
- photos как supplemental evidence;
- mixed input.

### 6.1. Правило источников истины

Приоритет должен быть таким:

1. Явное объяснение пользователя.
2. Печатный текст или документ с извлеченным текстом.
3. Структурированные справочники (`DEKEL`, `MAVNADIM`, mapping rules, template rules).
4. Handwriting как low-confidence source.
5. Photo evidence как supplemental source, но не как самостоятельная source of truth.

### 6.2. Правило по handwriting

Handwriting допускается как вход, но:

- не считается автоматически надежным фактом;
- используется как источник гипотез;
- при низкой уверенности переводится в review-only слой;
- не должен silently менять scope или расчет без подтверждения.

### 6.3. Правило по sample documents

Материалы в `HOMER/MISMAH LE DUGMA` используются как reference для формы итогового документа, а не как runtime input пользователя по умолчанию.

## 7. Источники данных системы

### 7.1. Template Source

Шаблон `מסמך משמעויות` задает:

- структуру разделов;
- обязательные и условные блоки;
- формат таблиц;
- формат итоговых сумм;
- формат текстовых секций;
- состав выходного пакета.

### 7.2. DEKEL

`DEKEL` - главный источник позиций, цен, единиц и расчетных строк для блока `אומדן`.

Система должна:

- читать live workbook;
- нормализовать строки;
- понимать главы и подглавы;
- учитывать units и section hints;
- использовать retrieval + scoring, а не только прямое совпадение слов.

### 7.3. MAVNADIM

`MAVNADIM` - отдельный источник готовых модульных объектов.

Он используется:

- когда кейс относится к готовым модульным сооружениям;
- как primary candidate source для самих модульных объектов;
- вместе с `DEKEL`, если нужны сопутствующие работы: фундамент, подводы, электричество, вода, канализация, подготовка площадки и т.п.

### 7.4. Supporting Evidence

Supporting evidence может дополнять объяснение пользователя, но не всегда обладает одинаковой силой:

- typed/document evidence может усиливать понимание кейса;
- handwriting требует осторожности;
- photos нуждаются в сверке с текстом;
- противоречивые evidence-сигналы обязаны вести к clarification или review.

## 8. Целевой результат

Система должна выдавать:

1. Главный документ `מסמך משמעויות`.
2. Подробный лист расчета.
3. Review / assumptions sheet.
4. Traceable output package с привязкой к выбранным позициям, warnings и принятым решениям.

## 9. Формат итогового документа

На текущем этапе мы понимаем, что документ как минимум содержит следующие типы блоков:

- `נתוני מסמך`
- `רקע`
- `מטרת המשימה`
- `תכולת הפרויקט`
- `אומדן`
- `הערות לאומדן`
- бюджетный / breakdown блок
- график / schedule блок
- risk management блок
- приложения / source materials

Важно:

- формат документа не должен зависеть от одной темы работ;
- меняться должно содержимое, а не базовая логика шаблона;
- текст в документе не должен писаться "с нуля свободно";
- каждый текстовый блок должен иметь понятный source-of-truth и правило генерации.

## 10. Текстовая политика документа

### 10.1. Типы текста

В системе должны существовать 4 типа текста:

1. `Fixed`
   - заголовки разделов;
   - служебные названия;
   - стабильные шаблонные элементы.

2. `Variable`
   - текст, который строится из данных кейса;
   - формулировки про конкретную работу;
   - scope-specific описание проекта.

3. `Derived`
   - суммы;
   - агрегированные строки;
   - derived remarks;
   - output from calculations and review.

4. `Conditional`
   - warnings;
   - assumptions;
   - risk notes;
   - optional sections;
   - appendices.

### 10.2. Источники текста

Текст должен собираться из:

- исходного объяснения пользователя;
- ответов на clarification;
- подтвержденных строк `DEKEL`;
- подтвержденных объектов `MAVNADIM`, если они участвуют;
- рассчитанных значений;
- warnings, assumptions и review decisions;
- шаблонной логики документа.

### 10.3. Что нельзя делать

- нельзя копировать чужой sample document как будто это runtime content;
- нельзя генерировать бизнес-значимый текст без привязки к фактам кейса;
- нельзя silently заполнять спорные места;
- нельзя выдавать красивый, но логически неподтвержденный текст как финальный документ.

## 11. Когда система должна спрашивать пользователя

Clarification обязателен, если:

- без ответа меняется смысл работы;
- не хватает критичных размеров, количества, длины, площади, глубины или unit;
- неясно, входит ли работа в scope;
- неясно, нужно ли включать ancillary works;
- handwriting / photo дает лишь гипотезу, а не надежный факт;
- для обязательного раздела документа не хватает данных;
- есть несколько правдоподобных трактовок с разным влиянием на расчет или текст.

Clarification не обязателен, если:

- данные уже явно присутствуют;
- блок является fixed boilerplate;
- значение надежно derived из подтвержденных фактов;
- предупреждение можно честно вынести в review-sheet без искажения главного документа.

## 12. Основной user flow

1. Пользователь создает кейс.
2. Пользователь передает объяснение работы и optional evidence.
3. Система делает preprocessing и work understanding.
4. Если данных не хватает - система задает уточняющие вопросы.
5. Система строит candidate matches в `DEKEL`.
6. При необходимости система строит candidate matches в `MAVNADIM`.
7. Пользователь или reviewer подтверждает релевантные позиции.
8. Система считает quantities, totals и aggregates.
9. Система собирает output draft.
10. Система формирует итоговый output package.
11. Пользователь или reviewer подтверждает финальный результат.

## 13. Функциональные требования

### 13.1. Intake

Система должна:

- принимать typed / document / mixed input;
- хранить raw input отдельно от normalized interpretation;
- поддерживать attachments / evidence;
- не смешивать source text и generated text.

### 13.2. Work Understanding

Система должна:

- извлекать типы работ;
- извлекать размеры, длину, площадь, count;
- различать primary works и possible ancillary works;
- строить structured work items;
- маркировать missing fields и low-confidence extraction.

### 13.3. Clarification

Система должна:

- генерировать точечные вопросы;
- не задавать лишние вопросы, если нужные данные уже извлечены;
- принимать ответы и пересчитывать кейс через тот же controlled pipeline;
- фиксировать trace по вопросам и ответам.

### 13.4. DEKEL Matching

Система должна:

- поддерживать lexical, semantic и chapter-aware retrieval;
- учитывать work-type-aware routing;
- учитывать units;
- учитывать, что отдельные работы могут тянуть строки из разных глав;
- не превращать chapter hints в жесткий запрет на другие релевантные главы;
- оценивать confidence и явно выводить candidates на review.

### 13.5. MAVNADIM Matching

Система должна:

- уметь выделять случаи с готовыми модульными объектами;
- рассматривать `MAVNADIM` как отдельный первичный источник;
- связывать modular object с optional ancillary works из `DEKEL`.

### 13.6. Calculation

Система должна:

- считать quantity корректно по типу работ;
- различать direct, derived и estimated quantity;
- явно маркировать estimated values;
- валидировать unit consistency;
- считать subtotal, fee rows и total.

### 13.7. Aggregation

Система должна:

- переносить line items в структуру шаблона;
- агрегировать суммы по правилам mapping;
- сохранять trace между source lines и output rows;
- не терять детализацию при переносе в шаблон.

### 13.8. Review

Система должна:

- показывать спорные совпадения;
- показывать assumptions;
- показывать warnings;
- позволять подтверждать / отклонять выбор;
- не выпускать сомнительный финальный результат без review-gate.

### 13.9. Output

Система должна:

- строить output draft;
- строить structured output package;
- экспортировать главный документ;
- экспортировать detailed cost sheet;
- экспортировать review / assumptions sheet;
- сохранять generated artifacts и manifest.

## 14. Нефункциональные требования

### 14.1. Прозрачность

Каждый значимый результат должен быть объясним:

- почему выбрана позиция;
- откуда взято количество;
- где возникло допущение;
- что подтверждено пользователем;
- что еще требует review.

### 14.2. Управляемость

Система не должна принимать критичные решения молча.

### 14.3. Повторяемость

Одинаковые входные данные должны приводить к повторяемому результату при одинаковых правилах и версии справочников.

### 14.4. Версионирование

Нужно уметь различать версии:

- шаблона;
- `DEKEL`;
- `MAVNADIM`;
- mapping rules;
- generated outputs.

### 14.5. Качество данных

Система должна быть устойчива к:

- шумным описаниям;
- смешанным языкам;
- частично неполным данным;
- shorthand-формату;
- низкоуверенным evidence-сигналам.

## 15. MVP-срез

### 15.1. Что уже должно считаться частью MVP

- controlled case pipeline;
- clarification loop;
- `DEKEL` live read;
- candidate retrieval;
- confirmed `DEKEL` selection;
- preliminary `אומדן`;
- output draft;
- output package;
- генерация export artifacts;
- template-driven main document in draft/export form;
- базовый `MAVNADIM` flow;
- review-gated output.

### 15.2. Что еще нужно довести внутри MVP

- более строгую текстовую политику по разделам документа;
- более точный mapping между section meaning и output wording;
- более надежный mixed-work balancing;
- более сильный retrieval на сложных кейсах;
- правила для ancillary works;
- явную matrix для `fixed / variable / derived / conditional` текста;
- доменную валидацию schedule и risk sections.

## 16. За пределами MVP

- полноценный industrial OCR layer;
- сложный multimodal understanding как primary mode;
- поддержка множества сильно отличающихся шаблонов;
- полный автоматический выпуск без human approval;
- глубокая интеграция с внешними корпоративными системами.

## 17. Основные риски

### 17.1. Продуктовые риски

- ожидание "магического AI", а не управляемого полуавтоматического инструмента;
- размытый scope первого релиза;
- слишком раннее расширение в сторону "все форматы, все кейсы, все шаблоны".

### 17.2. Технические риски

- слабый matching на реальных кейсах;
- неверная работа с unit / quantity;
- слабый mapping из line items в шаблон;
- heuristic schedule и risk sections без доменной валидации;
- несогласованность between runtime behavior and document wording.

### 17.3. Риски данных

- шумный или неполный input;
- плохое качество handwriting;
- фото без достаточного контекста;
- неоднозначности в `DEKEL`;
- несинхронность версий справочников.

### 17.4. Риски текста и формата

- неверная формулировка scope;
- слишком свободная генерация текста;
- смешение factual text и guessed text;
- ошибочное заполнение обязательных разделов без нужных данных;
- расхождение между формой шаблона и реальным содержанием кейса.

## 18. Метрики успеха

Для MVP продукт должен стремиться к следующим показателям:

- сокращение времени подготовки кейса по сравнению с полностью ручной работой;
- снижение количества ручных ошибок в `אומדן`;
- доля кейсов, проходящих controlled pipeline без системного сбоя;
- доля кейсов, где clarification был достаточным и не чрезмерным;
- доля top candidates, которые reviewer считает релевантными;
- доля документов, которые не требуют полной ручной пересборки;
- прозрачность output: reviewer понимает, откуда взялись строки и суммы.

Точные целевые значения пока требуют отдельного согласования после серии живых кейсов.

## 22. Правила ведения этого PRD

Этот PRD должен обновляться при любом существенном изменении:

- продуктовой логики;
- MVP scope;
- типов входа;
- правил clarification;
- логики matching / calculation / aggregation;
- формата шаблона;
- текстовой политики документа;
- output package.

При обновлении PRD нельзя:

- молча менять product scope без отражения в документе;
- объявлять feature завершенной без явного acceptance meaning;
- заменять open question предположением без фиксации решения.

## 23. Definition of Done для проекта

Проект можно считать продуктово завершенным только когда:

- система уверенно принимает реальные кейсы в ожидаемых форматах;
- clarification работает точечно, а не хаотично;
- matching по `DEKEL` проходит живые кейсы на приемлемом уровне;
- `MAVNADIM` корректно обрабатывается как отдельный тип сущности;
- `אומדן` собирается корректно и объяснимо;
- итоговый `מסמך משמעויות` соответствует рабочему формату;
- текст документа формируется по понятным и контролируемым правилам;
- reviewer может понять происхождение каждой важной части output;
- проектная команда считает результат пригодным для реальной работы.
