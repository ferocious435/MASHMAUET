Ты — ведущий системный инженер по навыкам (skills), оркестрации агентов и архитектуре рабочих контуров в Codex / Antigravity.

Твоя задача:
не просто установить skills, а построить полноценную управляемую систему skills для проекта AI-системы автоматической подготовки “מסמך משמעויות” по описанию работ, фото, размерам, шаблону и מחירון.

Главная цель:
создать стабильную, понятную, масштабируемую и управляемую skill-инфраструктуру, в которой:
- каждый skill установлен осознанно
- у каждого skill есть роль, зона ответственности и границы применения
- есть центральный skill-router
- есть manager / registry / governance слой
- есть правила, когда какой skill включается
- есть правила передачи задачи между skills
- есть правила работы нескольких skills в цепочке
- есть правила параллельной и последовательной работы
- есть правила контроля качества, логирования и проверки результата
- нет хаоса, дублирования и конфликтов между skills

Работай как архитектор production-grade skill ecosystem, а не как установщик отдельных папок.

================================
1. КОНТЕКСТ ПРОЕКТА
================================

Проект:
AI-система подготовки “מסמך משמעויות”.

Система должна:
- принимать описание предстоящих работ
- принимать фото
- принимать размеры
- использовать шаблон документа
- использовать מחירון с большим количеством позиций
- понимать тип и состав работ
- находить релевантные позиции в מחירון
- рассчитывать стоимость
- агрегировать суммы по строкам шаблона
- формировать итоговый документ
- вести внутренний расчет
- помечать спорные, вероятные и неуверенные совпадения
- поддерживать review flow

Это не просто AI-чат.
Это инженерно-расчетная документная система.

Поэтому skill-system должна покрывать:
- product planning
- architecture
- backend
- database
- AI / RAG / retrieval / matching
- testing
- debugging
- security
- documentation
- UI/UX
- orchestration
- skill governance

================================
3. ЧТО ИМЕННО НУЖНО СДЕЛАТЬ
================================

Выполни работу в 8 слоях.

--------------------------------
СЛОЙ A. INSTALLATION
--------------------------------

1. Установи все перечисленные skills корректно.
2. Проверь, что каждый skill реально существует в системе и доступен для вызова.
3. Если есть дубликаты, конфликты или несколько версий:
   - выяви это
   - определи приоритетную версию
   - зафиксируй решение
4. Если часть skills уже установлена:
   - не дублируй без причины
   - проверь их состояние
   - нормализуй структуру
5. Обеспечь чистую и понятную структуру директорий skills.
6. Убери мусор, дубли и неиспользуемые конфликтующие копии, если они мешают работе.

--------------------------------
СЛОЙ B. SKILL REGISTRY
--------------------------------

Создай централизованный реестр skills.

Для каждого skill зафиксируй:
- имя
- краткое назначение
- зону ответственности
- когда должен вызываться
- когда не должен вызываться
- входной тип задачи
- выходной тип результата
- кто его активирует
- какой skill может передать ему задачу
- какому skill он передает результат дальше
- можно ли запускать его параллельно
- можно ли запускать его повторно
- нужен ли human review после его работы
- приоритет
- уровень критичности
- принадлежность к группе

Сделай это не как хаотичный список, а как нормальный registry / routing manifest.

--------------------------------
СЛОЙ C. SKILL MANAGER
--------------------------------

Построй отдельный слой управления skills.

Skill Manager должен отвечать за:
- discover
- enable / disable
- status check
- dependency awareness
- conflict detection
- duplicate detection
- skill health
- routing metadata
- version awareness
- usage policy
- logging
- fallback logic

Skill Manager должен быть “центральным администратором skills”, а не просто папкой с файлами.

Определи:
- кто управляет Skill Manager
- какой skill является главным администратором
- какой skill отвечает за поддержку списка skills
- какой skill отвечает за проверку целостности skill-system
- какой skill отвечает за изменение правил роутинга

Ожидаемая логика:
- manage-skills = главный административный слой
- antigravity-skill-orchestrator = исполнитель маршрутизации
- loki-mode = верхнеуровневый операционный режим для длинных комплексных задач

--------------------------------
СЛОЙ D. SKILL ROUTER
--------------------------------

Построй полноценный router.

Нужен центральный skill-router, который должен:
- анализировать тип задачи
- определять категорию задачи
- решать, какой skill или группа skills должна работать
- определять порядок вызовов
- определять последовательный или параллельный режим
- определять, нужен ли review / validation перед следующим этапом
- вести trace маршрута

Router должен уметь обрабатывать минимум следующие категории задач:

1. Product / discovery / brainstorming
2. PRD / scope / roadmap
3. Architecture / system design
4. Database / schema / storage
5. API / backend design
6. Backend implementation
7. AI / RAG / retrieval / matching / evaluation
8. Document generation / template flow
9. Frontend / UX / review screens
10. Testing / QA
11. Debugging / incident resolution
12. Security / hardening / audit
13. Documentation / diagrams / API docs
14. Data import / normalization / pipelines
15. Skill governance / self-maintenance

Для каждой категории:
- определи primary skill
- secondary skill
- support skills
- validation skill
- fallback skill

СЛОЙ F. ПРАВИЛА РАБОТЫ SKILLS
--------------------------------

Для каждого skill и каждой группы определи:

1. Когда skill запускается автоматически
2. Когда запускается только по условиям
3. Когда не должен запускаться
4. Какие входные данные он ожидает
5. Какой артефакт должен вернуть
6. Кто проверяет его результат
7. Куда этот результат передается дальше

Построй правила передачи между skills.

Примеры логики:

- Product Group → передает validated requirements в Architecture Group
- Architecture Group → передает system/module specs в Backend Group + Data Group + AI Group
- AI Group → передает retrieval/matching strategy в Backend Group и Testing Group
- Backend Group → передает реализацию в Testing & Debug Group
- Testing Group → возвращает bugs / gaps обратно в Backend Group
- Security Group → проверяет backend и API до выхода в production-like state
- Docs Group → документирует утвержденные решения, а не черновой хаос
- Skill Governance Group → контролирует, чтобы маршруты выполнялись корректно

Сделай явные правила:
- последовательный режим
- параллельный режим
- режим с review checkpoint
- режим rollback / fallback
- режим повторного запуска после исправлений

--------------------------------
СЛОЙ G. ПАРАЛЛЕЛЬНАЯ И ПОСЛЕДОВАТЕЛЬНАЯ РАБОТА
--------------------------------

Определи, какие группы и skills могут работать параллельно, а какие только последовательно.

Обязательные правила:

Параллельно можно:
- Product Group + preliminary Architecture thinking
- Backend Group + Data Group после утверждения architecture
- AI Group + Data Group при проектировании retrieval/matching
- Docs Group параллельно с утвержденной architecture и approved implementation
- Security Group частично параллельно с implementation review
- UX Group параллельно с backend API contract design

Последовательно должны идти:
- clarification → requirements → architecture
- architecture → core backend/data design
- data normalization → reliable retrieval/matching
- matching logic → evaluation / QA
- approved aggregation logic → document generation
- final implementation → security audit → final release readiness

Задай правила блокировок:
- нельзя финализировать output pipeline без validation aggregation logic
- нельзя считать skill complete без traceable result
- нельзя пропускать review после doubtful / high-risk stages
- нельзя запускать финальный document output, если testing/security gates не пройдены для соответствующего слоя

--------------------------------
СЛОЙ H. GOVERNANCE, LOGGING, CONTROL
--------------------------------

Нужна система контроля работы skills.

Обязательно реализуй:

1. Логирование:
- какой skill был вызван
- по какой причине
- кто его вызвал
- какие входы получил
- какой результат вернул
- какой следующий skill получил его результат
- был ли результат принят или отклонен

2. Traceability:
- полный маршрут по skills для каждой сложной задачи
- возможность понять, где был сбой

3. Health checks:
- skill installed
- skill enabled
- skill callable
- registry entry exists
- routing rule exists
- no broken dependency
- no critical duplicate

4. Fallback rules:
Если основной skill недоступен или дал слабый результат:
- использовать secondary skill
- если нужно, эскалировать в reviewer / human check
- не продолжать слепо pipeline при критической неопределенности

5. Change control:
- любые изменения в routing rules должны фиксироваться
- любые изменения в active skill set должны фиксироваться
- любые изменения в group structure должны фиксироваться

================================
5. ОБЯЗАТЕЛЬНЫЙ ФОРМАТ РЕЗУЛЬТАТА
================================

Работай до завершенного результата.

В конце покажи результат в строгой структуре:

A. Installed Skills
- полный список установленных skills
- статус каждого
- замечания по конфликтам / дублям / версиям

B. Skill Registry
- для каждого skill: роль, ответственность, вход, выход, условия запуска, ограничения

C. Skill Groups
- группы
- состав
- лидер группы
- зона ответственности
- зависимые группы
- параллельность / последовательность

D. Skill Router
- routing logic по категориям задач
- primary / secondary / validator / fallback
- handoff map

E. Governance
- кто главный skill-manager
- кто поддерживает registry
- кто поддерживает routing
- кто проверяет целостность skill-system
- кто отвечает за обновления

F. Execution Policy
- что идет последовательно
- что идет параллельно
- где обязательный review
- где обязательная остановка при неопределенности

G. Logs and Audit
- как ведется логирование
- как отслеживается маршрут
- как выявляются ошибки orchestration

H. Final Recommendation
- какие skills критичны
- какие secondary
- какие стоит отключить по умолчанию
- какие risks остаются

================================
6. КРИТИЧЕСКИЕ ПРАВИЛА
================================

- Не делай поверхностный результат.
- Не давай абстрактный список.
- Не ограничивайся установкой.
- Построй рабочую систему orchestration и governance.
- Учитывай, что skills должны реально помогать разработке именно этой AI-системы.
- Не подключай нерелевантные skills просто “на всякий случай”.
- Делай routing детерминированным и понятным.
- Убирай хаос и дублирование ответственности.
- Если видишь, что какой-то skill лишний, конфликтует или должен быть secondary — так и зафиксируй.
- Сначала думай как системный архитектор skill-ecosystem, потом как установщик.

Начинай.
