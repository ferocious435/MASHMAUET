# Техническое ТЗ для разработчиков

## Проект: AI-система автоматической подготовки “מסמך משמעויות” по описанию работ и מחירון

---

## 1. Цель разработки

Разработать рабочую систему, которая:

* принимает описание предстоящих работ
* принимает фото
* принимает базовые размеры
* использует шаблон **“מסמך משמעויות”**
* использует большой **מחירון**
* подбирает релевантные позиции из מחירון
* считает стоимость
* агрегирует суммы по строкам шаблона
* генерирует готовый заполненный документ
* сохраняет внутренний детальный расчёт
* явно показывает спорные места, допущения и неуверенные совпадения

---

## 2. Основной принцип системы

Система не должна “угадывать молча”.

Правила:

* если данных не хватает — запросить уточнение
* если совпадение неуверенное — показать варианты
* если единица измерения не совпадает — поднять флаг
* если нет mapping в шаблон — не вставлять автоматически
* если расчёт частично предположительный — явно это отметить
* в финальный шаблон автоматически попадают только:

  * точные позиции
  * подтверждённые вероятные позиции

---

## 3. MVP-границы

### В MVP входит:

* обработка одного типа шаблона **“מסמך משמעויות”**
* работа с одним подготовленным מחירון
* ввод текста
* ввод размеров
* загрузка фото
* извлечение типов работ
* подбор позиций
* расчёт
* агрегация по шаблону
* review step
* генерация итогового документа
* генерация внутреннего расчётного листа
* генерация листа допущений / спорных мест

### В MVP не входит:

* обязательный анализ видео
* полностью автономный режим без проверки
* поддержка произвольных шаблонов без настройки
* сложное автообучение
* глубокие ERP-интеграции
* OCR плохих сканов как обязательная функция

## 5. Основной pipeline

### Шаг 1. Intake

Система принимает:

* case title / ID
* описание работы
* размеры
* фото
* шаблон
* מחירון
* дополнительные комментарии

### Шаг 2. Preprocessing

Система:

* нормализует текст
* извлекает числа, размеры, единицы
* индексирует фото
* проверяет наличие обязательных входов
* валидирует, что шаблон и מחירון доступны

### Шаг 3. Work Understanding

Система строит структурированную карту работ:

* основной тип работы
* дополнительные операции
* потенциальные скрытые работы
* объёмы
* список missing inputs

### Шаг 4. Clarification

Если есть missing critical data:

* система генерирует уточняющие вопросы
* ждёт ответы пользователя
* пересчитывает карту работ

### Шаг 5. Matching

Система ищет релевантные позиции в מחירון:

* keyword search
* semantic search
* section-aware filtering
* unit-aware filtering
* hidden-work expansion

### Шаг 6. Scoring

Каждой найденной позиции присваивается:

* confidence_score
* match_reason
* unit_status
* mapping_status
* requires_review

### Шаг 7. Calculation

Система считает:

* quantity
* unit_price
* line_total

### Шаг 8. Aggregation

Система переносит внутренние позиции в строки шаблона через mapping table

### Шаг 9. Review

Пользователь / reviewer видит:

* что система поняла
* какие позиции выбраны
* что попало в шаблон
* что требует проверки
* какие есть допущения

### Шаг 10. Output

Система генерирует:

* итоговый “מסמך משמעויות”
* внутренний расчётный лист
* лист проверки / допущений

## 10. Внутренняя логика matching

Matching не должен быть одним поиском по словам.

Нужен multi-layer matching:

### Layer 1. Lexical match

* совпадение по словам
* совпадение по корням
* совпадение по кодам / разделам

### Layer 2. Semantic match

* смысловое сходство описания работ и позиции מחירון

### Layer 3. Unit filter

* отбрасывание кандидатов с неподходящей единицей измерения

### Layer 4. Section relevance

* усиление кандидатов из релевантных разделов

### Layer 5. Hidden-work expansion

* добавление типовых сопутствующих работ

### Layer 6. Business rules

* правила, специфичные для шаблона и домена

---

## 11. Confidence model

Каждой позиции нужен score, например 0–1.

Пороговая логика MVP:

* 0.85–1.00 = exact
* 0.60–0.84 = probable
* ниже 0.60 = doubtful

Правила:

* exact можно предлагать как автоподтверждённые кандидаты
* probable требуют review пользователем
* doubtful не должны попадать в шаблон автоматически

---

## 12. Правила расчёта количества

Система должна поддерживать минимум 3 режима:

### 12.1. Direct quantity

Количество пришло явно от пользователя

### 12.2. Derived quantity

Количество вычислено из размеров
Примеры:

* площадь = длина × ширина
* длина = сумма отрезков
* количество = указанное число единиц

### 12.3. Estimated quantity

Количество предположено
Такой режим обязательно помечается флагом estimation_flag

---

## 13. Правила валидации

Перед финальной генерацией система обязана проверить:

1. шаблон выбран
2. מחירון выбран
3. обязательные поля кейса заполнены
4. все aggregated lines имеют валидные суммы или обоснованную пустоту
5. нет line_total < 0 без правила
6. единицы измерения согласованы
7. все doubtful items исключены из финального шаблона
8. итоговая сумма документа = сумме aggregated lines
9. если есть missing critical data — документ получает статус preliminary

## 20. Acceptance criteria по модулям

### Template Engine

Приёмка:

* умеет заполнять все обязательные поля шаблона
* корректно вставляет агрегированные суммы
* не ломает формат документа

### Pricebook Engine

Приёмка:

* умеет импортировать מחירון
* умеет искать по коду / словам / смыслу
* умеет фильтровать по unit и section

### Matching Engine

Приёмка:

* выдаёт ranked candidates
* присваивает confidence
* объясняет причину выбора

### Calculation Engine

Приёмка:

* корректно считает totals
* валидирует unit
* помечает estimation cases

### Aggregation Engine

Приёмка:

* правильно применяет mapping
* строит суммы по строкам шаблона
* даёт traceability до исходных позиций

### Output Package Engine

Приёмка:

* генерирует 3 файла
* суммы сходятся
* warnings вынесены отдельно

## 21. Ключевые риски для разработки

1. Плохая подготовка מחירון
2. Слабый mapping layer
3. Смешение UI-логики и расчётной логики
4. Отсутствие audit trace
5. Слишком ранняя попытка сделать “полный AI-автопилот”
6. Недостаточный контроль единиц измерения
7. Попытка вставлять спорные позиции в финальный документ автоматически

## 22. Главный технический принцип

Система должна строиться не вокруг “чата”, а вокруг **контролируемого расчётного pipeline**.

Основа архитектуры:

* структурированные данные
* движок правил
* explainable matching
* validation
* review step
* reproducible outputs

---

## 23. Краткая формулировка задачи для команды

Нужно построить инженерно-документный pipeline, который:

* принимает кейс
* интерпретирует работы
* находит правильные позиции מתוך מחירון
* считает стоимость
* агрегирует суммы по правилам шаблона
* даёт человеку review control
* выпускает готовый “מסמך משמעויות”

Главный фокус разработки:
**не генерация текста, а точный controlled matching + aggregation + document output.**
